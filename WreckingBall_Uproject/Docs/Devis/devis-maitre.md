## Direction du jeu (mise à jour du 2026-11-19, 19 h 46 à 20 h 09)
Le jeu devient un **soccer plus traditionnel en 3 contre 3** : toujours 6 personnages sur le terrain, les humains (1 à 4, manettes actives) en prennent un chacun (toujours la première place de leur équipe), l'IA contrôle les autres. La destruction de l'environnement reste au cœur du plaisir. Conséquences :
- **Phase E (probablement la prochaine phase de travail)** : match à 6, `BP_TeamSpawnPoint` par équipe (3 places + point principal où apparaît le ballon ; repli côte à côte autour de (0, 0, 0) sur le NavMesh), passe (le receveur devient détenteur du ballon), caméra sur le ballon et son porteur (ballon libre = ballon seul), sphères P1…P4 à la couleur d'équipe sur les bordures pour les humains hors écran. `ToggleBots` conservé : l'IA ne démarre pas au Play (debug).
- **Menus et interface de menu à passer au 3 contre 3 : design pending** (en attente du design de l'utilisateur ; aucun travail avant).
- **Couleurs d'équipe** : bleu et rouge pour l'instant ; **à terme, changeables** (mauve, rose, vert…). Dès la phase E, aucune couleur codée en dur : tout lit la définition d'équipe.
- **Phase F : nouvelle mouture de l'IA** (devis `claude/devis-npc.md`). Chaque équipe a un **Attaquant**, un **Défenseur** et un **Gardien**, dirigés par un **manager d'équipe omniscient**. Un seul niveau de difficulté pour commencer. Résumé :
  - Ballon libre ou adverse : Attaquant = souvent le plus proche du ballon ; Défenseur = dans un rayon depuis son filet égal à la distance entre les filets ÷ 2 ; Gardien = 3 m devant la boîte de collision de son filet, en mode Défense dans la boîte.
  - Ballon à l'équipe : le Défenseur devient attaquant (angle mort, parfois devant le ballon) ; le Gardien monte en restant le plus proche de son but.
  - Objets : le Défenseur lance des objets (toutes les 4 s, force variable), surtout vers l'attaquant adverse ; le Gardien, si le ballon est loin, barricade son filet en lançant au minimum jusqu'à 3 gros objets ; l'adversaire peut les retirer.

## Étape 5 — lot 4 fait le 2026-11-12 (soir), testé et commité par l'utilisateur
`BP_Destructible` (`/Game/Blueprint/Impact/Destructible/`, **renommé `BP_Destructible_Base` depuis**), compilé avec avertissements comme erreurs et sauvegardé.
- `ApplyImpact` (interface `BPI_ImpactReceiver`) : profil du destructible valide et état ≠ Destroyed → `GetSourceProfile` (locale `SourceProfile`) → `CanDamage` faux = refus → `TryRegisterHit` (debounce) → source sans profil = feedback léger, refus → `ComputeImpactDamage` (locale `Damage`) → sous `MinDamagePerHit` = feedback léger + print, refus → `ComputeNewHealth` (MaxStatesPerHit) → `CurrentHealth` (plancher 0) → feedback lourd → `OnDamaged` → `GetStateForHealth` → `SetDestructibleState` → print → Accepted = vrai. **Accepted = l'impact a retiré de la vie.** Écart d'ordre au devis : le debounce passe avant le cas « source sans profil », pour ne pas répéter le feedback léger à chaque frame de contact.
- `GetStateForHealth` : ≤ 0 → Destroyed ; sous `DamagedThresholdPercent` de (MaxHealth × HealthMultiplier) → Damaged ; sinon Intact.
- `SetDestructibleState` : si l'état change → Set `CurrentState` → `OnStateChanged` → Switch : Damaged → `OnEnterDamaged`, Destroyed → `OnEnterDestroyed` (points d'accroche, toujours à faux).
- `PlayImpactFeedback` → `Handled` : surface de l'impact, sinon celle du profil ; son (`PlaySoundAtLocation`) et Niagara (`SpawnSystemAtLocation`, rotation depuis la normale) ; faux si le destructible n'a pas de profil.
- `GetFeedbackSound` / `GetFeedbackFX` : Map lourde ou légère de `PDA_ImpactFeedback`, entrée de la surface, sinon entrée `SurfaceType_Default` ; None si rien.
- **Correctif de `BuildImpactDataFromHit`** (2 entrées ajoutées : `OtherComp`, `NormalImpulse`) : au moment d'un `OnComponentHit`, `GetVelocity` de la source donne déjà la vitesse **après** le rebond. Pour une source qui simule, la vitesse d'avant le choc est reconstituée : vitesse ± NormalImpulse ÷ masse. **Corrigé le 2026-11-12 (21 h 35, étape 6) : on garde la plus petite des deux.** Surface = `GetSurfaceType(Hit)`.
- Test : `Test/BP_Destructible_TestCube` (enfant, `TestMesh` cube 2 m, Hit Events, OnComponentHit → `BuildImpactDataFromHit` → `ApplyImpact` ; profil `DA_DestructibleWall_Plaster_Default`, `DebugFallbackSourceProfile` = `DA_BallPhysics_Soccer`). `DebugPrint` du CDO passé à faux le 2026-11-13. - Leçons outillage : `!=` et `==` du DSL échouent sur un enum (utiliser `Utilities|Enum|NotEqual(Enum)` / `Equal(Enum)`) ; un enum littéral en entrée de ces nodes échoue aussi : brancher une valeur provisoire, puis `break_pins` + `set_pin_value`. `Utilities|IsValid` dans une expression devient le macro (exec) : utiliser la forme à continuations.
